# OmniShelf database backup and recovery

## Automated backup

The `OmniShelf encrypted Neon database backups` workflow creates a daily PostgreSQL custom-format dump of the **Neon primary branch's `neondb` database**, encrypts it with GnuPG AES-256 before upload, verifies that it decrypts and remains a valid PostgreSQL archive, then uploads only the encrypted archive and a SHA-256 checksum to the private Backblaze B2 bucket.

The schedule is 02:30 UTC (08:00 India Standard Time). A manual run requires selecting `yes` in the workflow's confirmation input. The workflow does not run on pull requests and has read-only repository permissions.

The backup workflow is independent of the OmniShelf 1.3.9 email-recovery application pull request. It does not deploy the application or change the Neon database.

## GitHub Actions repository secrets

Add these under **Repository → Settings → Secrets and variables → Actions → Repository secrets**:

| Secret | Value |
|---|---|
| `NEON_DATABASE_URL` | Neon **primary/main branch**, database `neondb`, **Direct (unpooled)** connection URL |
| `BACKUP_ENCRYPTION_PASSPHRASE` | A unique, high-entropy passphrase generated by a password manager |
| `B2_APPLICATION_KEY_ID` | The key ID of the bucket-restricted Backblaze application key |
| `B2_APPLICATION_KEY` | The one-time Backblaze application key secret |

Do not use a pooled Neon URL: Neon documents that `pg_dump` and `pg_restore` require a direct, unpooled connection. The workflow checks for a direct Neon host and the `neondb` database before it proceeds.

Keep a separate offline/password-manager copy of the encryption passphrase. GitHub cannot reveal a saved secret again. If the passphrase is lost, the encrypted backups cannot be recovered. Never put credentials in repository files, issues, commits, or chat.

The B2 application key should be restricted to the `omnishelf-db-backups` bucket and the `omnishelf/` prefix. The workflow uses the bucket's S3 endpoint:
`https://s3.us-east-005.backblazeb2.com`.

## Backblaze retention

Configure a lifecycle rule in the Backblaze bucket UI for the `omnishelf/` prefix:

- Hide files 30 days after upload.
- Permanently delete hidden files 1 day after they are hidden.

This keeps roughly 30 days of daily backups without requiring the workflow's upload key to have delete permission. Lifecycle processing runs periodically, so actual removal may occur later than the exact day boundary.

## Recovery outline

1. Download both the `.dump.gpg` object and its matching `.dump.gpg.sha256` file from the B2 bucket.
2. Verify the encrypted file checksum with `sha256sum -c <backup-file>.gpg.sha256`.
3. Decrypt the archive locally with GnuPG using the saved passphrase.
4. Restore into a **new, isolated Neon branch/database or disposable PostgreSQL instance**, never over the live `main` database:
   `pg_restore --exit-on-error --no-owner --no-acl --dbname="<isolated direct PostgreSQL URL>" <decrypted-backup.dump>`.
5. Confirm the Alembic version, application tables, and representative data before considering the restore successful.

A successful scheduled upload and archive inspection is not, by itself, a completed restore drill. The release checklist remains open until a real isolated restore has been tested and documented.
